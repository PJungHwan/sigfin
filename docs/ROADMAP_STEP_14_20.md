## 3. STEP 14 — 가상 포트폴리오 관리

### 목표

BTC·ETH 보유량과 USDT 현금, 사용자가 직접 기록한 가상 거래, 비용, 실현/미실현 손익을 한 계좌 단위로 설명할 수 있게 한다. 기존 단일 종목 백테스트 결과와 구분되는 **교육·연구용 수동 원장**을 만든다.

### 확정 범위

- 기본 원금은 기존과 같은 10,000 USDT로 두되 변경 가능하게 한다.
- 한 세션의 가상 포트폴리오 1개, USDT 현금과 BTC/ETH의 양수 보유량, 무레버리지로 제한한다. 보유 수량 이내 매도만 허용한다.
- 사용자가 입력을 확인하고 기록 버튼을 눌렀을 때만 가상 매수/매도를 반영한다. 시세 새로고침·AI 결과·전략 신호는 원장을 바꾸지 않는다.
- 가상 체결가는 선택한 기준 가격과 설정한 불리한 슬리피지로 계산한 가정값이다. 실제 거래소 체결이나 같은 봉 종가 신호의 실제 체결 가능성을 뜻하지 않는다.
- 자산 평가는 UTC의 공통 확정 봉 마감에 맞춘 실제 종가를 사용한다. 가격의 출처·봉·마감/수집 시각을 저장한다.
- 필요한 보유 자산의 가격이 없거나 공통 평가 시각을 확보하지 못하면 전체 평가를 불완전/N/A로 표시한다. 현금·기존 원장은 보존하고 가격을 임의 대체하지 않는다.
- STEP 14는 세션 범위의 원장만 지원한다. 서버 재시작 후 복원, 파일/DB 저장과 불러오기는 STEP 15에서 구현한다. 시세 캐시를 계좌 저장소로 사용하지 않는다.
- 추가 입출금, 과거 거래 소급 입력, FIFO 세금 계산, 여러 계좌, 숏/증거금·자동 리밸런싱·주문 자동화는 확정 범위에서 제외한다. 범위 변경은 별도 작업으로 기록한다.

### 회계 기준

기존 [백테스트 회계](backtesting.md)의 **모든 지급 수수료를 계좌 실현 손익에 포함**하는 기준을 재사용한다. 포트폴리오의 평균 매입가는 체결가 기준이고 진입 수수료를 매입가에 다시 더하지 않는다.

```text
가상 매수 체결가 = 기준가 × (1 + 편도 슬리피지)
가상 매도 체결가 = 기준가 × (1 - 편도 슬리피지)
거래 수수료 = 수량 × 가상 체결가 × 편도 수수료율

매수: 현금 -= 수량 × 체결가 + 수수료
      새 평균 매입가 = (기존 수량 × 기존 평균 매입가 + 매수 수량 × 매수 체결가) / 새 총수량
      실현 손익 -= 지급 수수료
매도: 현금 += 수량 × 체결가 - 수수료
      실현 손익 += 매도 수량 × (체결가 - 평균 매입가) - 수수료

총자산 = 현금 + Σ(보유 수량 × 평가 종가)
미실현 손익 = Σ(보유 수량 × (평가 종가 - 평균 매입가))
총자산 = 초기금 + 누적 실현 손익 + 미실현 손익
```

슬리피지는 체결가에 반영된 비용이므로 손익에서 다시 차감하지 않는다. 평균 매입가는 수량 가중평균이며 전량 매도 후에는 N/A로 표시하고 다음 매수에서 새로 초기화한다. 추가 입출금이 없는 최초 범위에서 위 등식을 검증한다. 금액/수량 정밀도·반올림/허용오차는 구현 전에 데이터 계약으로 확정한다.

여러 번 매수/일부 매도를 지원하되 기존 백테스트의 단일 포지션·전량 청산 정책은 변경하지 않는다. 수동 원장은 호가·거래량 기반 체결 모델을 제공하지 않는다는 가정을 표시하고, 백테스트의 거래량 제한과 혼동하지 않는다.

### 선행 조건

확정된 수동 원장/현금+양수 보유 범위를 적용한다. SF-14-01에서 비용·정밀도·평가 시각과 초기금 변경 정책을 명세한다. 초기금 변경은 거래 전 또는 명시적인 새 가상 계좌 생성에서만 허용해 기존 원장에 소급 반영하지 않는다. 기존 수집 서비스와 `adverse_fill_price` 등 순수 비용 공식은 재사용하되 백테스트 엔진을 다중 자산 엔진으로 재작성하지 않는다.

### 완료 기준

두 자산의 연속 기록/일부 매도 후 현금·수량·손익 등식이 일치하고, 모든 이벤트에서 현금/보유량이 유효해야 한다. 원장과 가격 평가·재실행은 분리되고 동일 세션의 화면 재실행에서 원장이 유지되어야 한다. STEP 14가 영구 저장/복원을 제공한다고 표시하지 않는다. 기존 STEP 1~13 회귀와 UI의 중복/오류 보존 테스트를 통과하고 가상 기록임을 화면에 표시해야 한다.

### 테스트 항목

- 합성 손계산 예제: 초기금 1,000, 슬리피지 0, 수수료 1%, 가격 100에 2개 매수 후 110에 1개 매도, 잔여 1개를 120으로 평가하면 현금 906.9·실현 6.9·미실현 20·총자산 1,026.9·총수수료 3.1이 되어야 한다. **향후 테스트 예상값이며 실행 결과가 아니다.**
- BTC/ETH 혼합·여러 번 매수·일부/전체 매도·거래 없는 현금 계좌, 수수료/슬리피지 중복 차감 방지.

- 표시 토글/재실행/이중 제출로 거래가 늘지 않음, 가격 실패 시 기존 원장 보존, 공통 시각/미확정 봉 차단.
- AppTest의 수동 기록/세션 초기화/상태 분리, 전략·AI 버튼이 포트폴리오 이벤트를 자동 생성하지 않음.

저장은 Python 3.11 표준 `sqlite3`를 채택했고 프로젝트 내부 `data/sigfin.sqlite3`를 기본 경로로 구현했다. 외부 서버/추가 라이브러리 없이 트랜잭션/rollback과 매개변수 SQL을 사용할 수 있는 점이 선택 이유다. 계좌 생성·명시적 저장 시 DB를 만들며 시험은 임시 DB를 사용한다. [STEP 15 구현/검증](steps/STEP_15.md), [Python sqlite3](https://docs.python.org/3.11/library/sqlite3.html).

로컬 단일 사용자용이며 활성 DB는 앱 종료 후 백업하고 OneDrive 동기화 중 동시 실행은 피한다. 사용자 요청 없는 외부 경로 이동/기존 파일 삭제는 하지 않는다. SHA-256은 손상 탐지용이며 인증/암호화가 아니다.

### 선행 조건

STEP 14의 스키마/원장 의미, 현재 Pydantic 결과 스키마·전략 JSON·실행 ID를 확인한다. 원장·캐시·저장된 평가를 구분하고, 민감정보 저장 허용 목록/보존 한도를 먼저 정한다.

### 완료 기준

서버 재시작 후 동일 원장을 복원하고 중복 이벤트를 한 번만 반영해야 한다. 실패한 저장은 롤백되어야 하며, 저장된 연구 입력으로 결정론적 계산을 재현해야 한다. 입력이 없어 재현할 수 없는 경우 이유를 표시해야 한다.

원시 시계열이 필요한 실험은 기존 수집 한도 내의 허용 컬럼만 명시적으로 보존한다. 해시만 저장하고 입력을 잃은 결과를 ‘재현 가능’으로 표시하지 않는다. 실제 LLM 출력은 조회/재검증 대상으로 저장하며 새 호출이 동일 출력을 보장한다고 표현하지 않는다. API 키·인증 헤더·예외 원문·내부 추론은 저장하지 않고, 기존 세션 비용 원장/승인도 영속 복원해 재사용하지 않는다.

### 테스트 항목

재시작/스키마 버전·이벤트 재생, 동일 ID 중복·경합·저장 중 예외/rollback, 잘못된 경로/SQL 입력, 손상/구버전 자료, 불필요한 비밀정보 보존 금지, 입력 해시/복원 결과 정합성, 과거 결과 조회 시 API 자동 재호출 금지.

재사용 근거: [전략 저장](../strategies/storage.py), [Workflow 결과 모델](../graph/state.py), [Risk 확장 결과](../graph/risk_state.py), [현재 세션 기반 UI](../ui/workflow_view.py).

### 실행·비용·모드 기준

- 기본 모드는 Mock이며 유료 호출이 없다. 통합 UI의 Live는 기존 `LLM Workflow` 경로에 대응한다. 모드 이름 변경을 이유로 기존 그래프 계약을 깨지 않는다.
- Live는 실행 버튼·본인 API 키·지원 모델/유효 가격·명시적 비용 승인·세션 한도를 모두 검사한다. **개발 방향 확정은 유료 API 실행 승인이 아니다.**
- 기존 기본 세션 5회/$0.25와 입력/출력 제한, 병렬 일괄 예약·중복 방지·Workflow 자동 재시도 0회 정책을 재사용한다. 가격 미확인/만료는 호출을 차단한다. 실패 요청 과금을 무료로 가정하지 않는다.
- 선택 모드와 실제 호출은 별개다. Live를 선택해도 자료 부족으로 로컬 결과를 만들면 `api_called=False`와 사유를 표시하고 실 LLM 응답으로 소개하지 않는다.
- Live에서의 실제 LLM 대상은 기존 Technical/Macro다. 기존 Mock Debate/Risk 그래프의 모드 제한과 금지 조합을 유지한다. 실 LLM Bull/Bear Debate·실 LLM Risk Manager는 이번 확정 범위에 포함하지 않는다.
- 포트폴리오 위험/과거 Mock 결과를 보고서에 함께 넣을 때 출처·실행 ID·모드·시각을 따로 표시한다. 다른 실행 결과를 동일한 Live 그래프의 산출물로 위장하지 않는다.
- 화면 재실행·기록 조회·보고서 다운로드는 시장/LLM 재호출이나 가상 거래를 자동 발생시키지 않는다.

### 완료 기준

기존 실행 경로를 통합 리포트에서 선택해 사용할 수 있고, 각 수치/주장의 원본 ID·값·단위·시각과 실제 호출 여부를 확인할 수 있어야 한다. 다른 조건/기간의 결과는 별도 문맥 또는 비교 불가로 표시한다. Mock/Live·로컬 생략·PARTIAL/FAILED·FRED 현재 개정값의 한계를 화면/저장/내보내기에서 동일하게 유지한다.

코드 연결·모의 HTTP·무승인 차단·성공/부분 실패·비용 정합성과 UI 회귀를 검증해야 한다. 실제 유료 테스트는 별도 승인/실행 조건을 갖춘 경우에만 수행하며, 하지 않았다면 **Live 지원 경로 검증 완료 / 실 계정 호출 미검증**으로 나눠 기록한다. 기본 자동 테스트 완료를 실제 계정 호출 성공으로 바꾸지 않는다.

보고서 조립은 결정론적 Python으로 수행하고 추가 LLM 호출을 만들지 않는다. PDF 등 추가 형식은 현재 범위 밖이다.

- Mock에서 SDK/HTTP 미호출, Live에서 키/승인/가격/예산/버튼 없을 때 차단, 자료 부족 시 역할별 호출 생략.

## 7. STEP 18 — 백테스팅 고도화

### 목표

졸업프로젝트 결과를 재현 가능한 실험으로 설명한다. 과거 수익률 비교와 AI 근거/오류 처리 품질을 분리해 평가하며, 실험 결과를 투자 성공 확률로 해석하지 않는다.

### 세부 기능

| 작업 ID | 세부 작업 | 결과물/범위 |
| --- | --- | --- |
| SF-18-01 | 고정 실험 명세 | 사용자 작성 전략 2개 이상·Risk 설정·초기금/비용·동일 데이터 범위·실행 기준 시각·해시 고정 |
| SF-18-02 | 전략/Risk 비교 표 | 기존 엔진을 재사용한 독립 실행, 수익률/종료 거래/승률/MDD/비용·무거래 N/A·실제 표본 표시 |
| SF-18-03 | 시간순 검토/검증 구간 | 앞 기간에서 조건 검토 후 전략을 고정하고 뒤 기간에서 별도 평가, 구간별 초기 상태·워밍업·체결 경계 명시 |
| SF-18-04 | 성과 검산·검증 보고 | 손계산/고정 fixture로 손익·비용·MDD/승률을 대조하고 표본/실패·재현성·연구 한계를 보고서와 연결 |

### 선행 조건

STEP 5~6 엔진·고정 fixture, STEP 15 스냅샷, STEP 17 보고 형식이 필요하다. 먼저 데이터 기간·분할 기준·전략·비용·평가 지표를 문서로 고정한다. 전략 탐색/최적화 결과를 검증 구간에 맞춰 다시 조정한 뒤 독립 검증이라고 부르지 않는다.

### 완료 기준

동일 입력의 결정론적 실행 결과가 같고 비교 표가 각 독립 실행과 일치해야 한다. 최소 전략 2개×Risk OFF/ON의 4개 조합을 동일 데이터·초기금·비용·거래량 참여율로 검증하고 일부 실패를 전체 비교 성공으로 표시하지 않는다. 시간순 검증에서 미래 구간으로 지표/조건을 보정하지 않고, 과거 워밍업 사용 범위와 첫/마지막 신호 체결 정책을 명시해야 한다. 기본안은 각 구간을 FLAT/동일 초기금으로 독립 시작한다.

현재 가상 원장 성과를 과거 백테스트에 소급 적용하지 않아야 한다. Macro 발표/빈티지 부족 정책도 유지한다. 근거 검증 시험의 성공은 미래 시장 예측 정확도 향상으로 표시하지 않는다.

### 테스트 항목

동일 스냅샷 반복·설정 차이만 있는 비교·순서 독립성, 구간 경계 다음 봉 체결/마지막 봉 금지, 미래 가격 변경의 과거 영향 차단, 비용/거래량 조건 일치, 손계산 성과·MDD·종료 거래 기준 승률·실현/미실현 손익, 무거래/소표본·결측 N/A, 실험 재조회 API 미호출과 기존 고정 결과 호환성.

실제 LLM 평가가 필요한지는 별도 결정 사항이다. 기본 자동 시험은 기존 모의 HTTP/합성 입력을 사용한다. 유료 검증은 계정 권한·현재 모델/가격·명시적 비용 승인·상한을 확인한 후에만 별도 실험으로 계획하며 미승인/미실행 상태를 그대로 기록한다.

재사용 근거: [백테스트 엔진](../backtest/engine.py), [위험 회귀 fixture](../tests/fixtures/step5_risk_off.json), [LLM 검증 테스트](../tests/test_llm_workflow.py), [Debate 검증](../tests/test_debate.py).

## 10. 공통 완료·검증 원칙

1. 순수 회계/통계와 UI/저장/호출을 분리하고 기존 collectors/indicator/strategy/backtest/LLM/graph 계약을 재사용한다. 신규 모듈의 실제 구현/미착수 상태는 각 단계 기록과 백로그를 따른다.
2. 각 작업의 기준을 소스·문서·테스트로 확인한 후에만 구현 상태를 완료로 바꾼다. 필수 실패는 해결하거나 미완료로 남긴다. 선택적 실 API 미실행은 사유를 기록하고 성공으로 합산하지 않는다.
3. 순수 계산은 pytest, 화면/상태는 AppTest, 실제 화면/파일 대화상자는 필요한 수동 시험을 사용한다. 기존 STEP 1~13 회귀·Risk OFF 고정 결과·Mock 경로 보존을 확인한다.
4. 미래 캔들/가격·공개 시점 미검증 Macro를 과거 입력에 넣지 않는다. 자료 부족은 N/A/UNKNOWN/부분 실패로 처리하고 가격·발표일·빈티지를 생성하지 않는다.
5. API 키/헤더·예외 원문·비공개 내부 추론을 입력/로그/DB/보고서에 남기지 않는다. 시세/LLM 캐시는 저장 원장을 대신하지 않는다.
6. Live 실행 승인/사용량·미확인 과금·실제 전송 여부를 구분한다. 조회/복원/화면 재실행은 유료 호출·가상 거래를 만들지 않는다.
7. 테스트 명령·환경·실제 결과·날짜·skip/실패/미검증 사유를 단계 기록에 남긴다. 예정 시험 수나 과거 통과 수를 이번 결과로 사용하지 않는다.
8. UI는 기존 밝은 디자인·Plotly·카드/CSS를 유지한다. 전체 UI/UX 리디자인은 **STEP 20 기능 개발 완료 후 별도**이며 현재 작업 수/완료 기준에서 제외한다.
9. 실제 주문·계정 연결·자동매매, 실 LLM Bull/Bear Debate/Risk Manager, 가상 숏/레버리지 포트폴리오·강제청산가, 시점 준수 Macro 수집, 중첩 전략, 외부 다중 사용자 배포는 이번 확정 범위에 추가하지 않는다.

## 13. 실제 검증 범위

초기 계획 정리의 정적 검토와 후속 STEP 14~17 개발 검증을 구분한다. 이번 후속 개발에서는 단계별 pytest/AppTest·전체 회귀·문법/import·의존성 검사와 로컬 Streamlit health를 확인했다. 최종 개수/명령/실패 해결은 [STEP 17](steps/STEP_17.md)에 기록한다.

최초 순차 구현 검증은 오프라인/모의 HTTP 중심이었고 후속 실제 Binance 가격 경로·Edge 검증은 STEP 16~17에 따로 기록됐다. 실제 Binance/FRED 통합 자료 대조와 실계정 OpenAI 유료 호출/청구는 별도 미검증이다. 2026-11-06 문서 점검에서는 테스트·서버·API를 재실행하지 않았다. 이후 STEP 18은 합성/모의 자료 전체 pytest·AppTest·문법/import·실제 서버 health를 확인했다. STEP 19~20 개발·새 라이브러리 설치·실제 주문·Git 커밋/Push는 수행하지 않는다.

STEP 18의 BTC/USDT 실제 브라우저 수동 검증은 사용자의 완료 통보로 별도 반영했다. 이를 외부 API 통합 자동 시험 14개나 Binance/FRED 통합 리포트·ETH·유료 LLM의 검증 완료로 확대하지 않는다. 이번 최종 정리는 문서만 수정하며 STEP 19 개발이나 테스트/서버/API 재실행은 하지 않았다.

위 문서 정리 이후 별도 요청의 STEP 19에서는 통합/오류 회귀·새 Python 3.11 환경·서버 health·격리 Edge의 합성 자료 흐름을 검증했다. 최신 자동 결과는 **638 passed / 0 failed / 14 skipped**다. 실제 시장 사용자 수동 검수·실 API 14개·실계정 유료 LLM은 구분하며, STEP 20과 전면 리디자인은 시작하지 않았다.

이후 **2026-11-12 STEP 20**에서는 최종 추적/README·13분 시연/별도 합성 경로와 회귀 검수를 진행했다. 최신 전체는 **646 passed / 0 failed / 14 skipped**, 별도 설치 환경 선택 9 passed, 격리 Edge의 12회 실험 JSON 재실행/해시 일치다([기록](steps/STEP_20.md)). 후속 사용자 확인으로 STEP 1~20 기능 구현과 오프라인 8533 접속·합성 차트/지표·기능 정상 동작을 기록했다. SF-20-01~03은 완료, SF-20-04는 발표 장비 전체 리허설·제출 형식/최종 수용을 남긴 진행 중이다. 실제 외부 API·유료 LLM·전면 리디자인은 미완료이며 사용자 DB/기존 계산은 보존했다.
